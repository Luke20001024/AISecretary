The product loop

核心不是聊天，而是一条可核验的“理解流水线”

点击任一节点查看它解决的问题。模型负责语义理解，确定性代码负责证据、安全和画像投影，用户负责随时修改或删除。

节点职责

先保住原始事实，再谈长期理解

原始日级记录始终是事实层；现有有效 responses、精确绑定的反馈和可定位证据构成派生理解层。新前端只改变呈现，不反写原始记录。

为什么必要

如果文章直接覆盖事实，用户删改一句话就会破坏历史；事实与解释分层才能让洞察可重建、可推翻。

Next increment · Context Review

下一增量：Agent 每天复核，但不是每天打扰

Daily Review 回看一天发生了什么；Context Review 判断新记录是否改变了值得长期复用的理解。两者复用运行时机，但产物、证据和用户授权彼此独立。

未实现边界：当前已安装前端只会在用户点击底部固定核对按钮时创建一次现有 Reflection request；它不是 Daily Review，也没有 08:00 / 21:00 调度、变化 gate 或历史 backlog。本节以下自动 Review 内容都是下一增量合同。

14 天不是展示范围：“她眼中的我”读取目前已形成且仍通过校验的累计理解，不能反向宣称覆盖从开始记录以来的全部历史。每次固定核对只把最近 14 个自然日内的可用日记、有效 Confirmed Context 与最近有效校准发送给 Worker；新结果再由确定性 reducer 累积进 profile。

继承当前设计，不另造管理后台：事实、模型解释和用户反馈继续分层；通过校验的理解直接进入可阅读结果，不要求用户逐条授权。只有旧 Context / Pack 的跨任务分发仍保留独立授权链路，并下沉到页面底部兼容区。自动 Context Review 只有用户明确启用后才接入现有 Daily Review 周期；两者只共享唤醒时机，不共享产物或成功状态。

01 · GATE

先做本地变化检查

先比较“实质变化水位”与上次成功状态；只有确实需要运行时才生成本轮 review_run_key。单纯日期推进或窗口自然老化不调用模型。

  • run_key 只负责幂等与审计
  • 晨晚检查不等于每天调用两次
02 · WINDOW

观察滚动 14 个自然日

先确定被核对的 target_date D，窗口严格为 D−13 至 D。历史不足时使用实际可授权的 N 个自然日。

  • 自然日跨度与有记录天数分开显示
  • 没有记录只代表缺少证据
03 · RECONCILE

先核对已经记住什么

输入为 target_date 对应增量、窗口内原始记录、相关已确认 Context 和相关用户决定反馈；候选证据仍必须回到原始文件与行级引文。

  • 识别强化、新增、变化与冲突
  • 不得把 AI 日总结当最终证据
04 · ATTENTION

由变化决定是否打扰

无变化安静结束；有效新 response 进入累计 profile 后，一个 active projected tag 对应一个阅读段落。旧版长期 Context 候选只出现在底部兼容区。

  • 核对不阻断当前 profile 阅读
  • 不形成每日审批队列

单候选优先级：同一次 Review 同时发现多项时，按“用户刚调整后产生的冲突 → 其他 conflict → update → new”选择一项；同级再按证据是否跨不同记录日、是否更接近 target_date 和影响范围排序。未选项不进入隐藏队列，只有后续出现新的实质变化、失败补跑或用户明确选择其他日期时才重新判断。

14 天的精确定义：D 永远表示被核对的 target_date，不是 worker 的运行日期：21:00 的 D 是今天，08:00 补查的 D 是昨天。窗口始终为 [D−13, D]。N 由用户本次授权范围内最早可用的记录日期决定，不由“产品启用了几天”决定；如果启用当天已经授权此前 14 天的记录，首次运行即可观察完整窗口。如果只拥有 9 个已授权自然日，且其中 5 天有记录，前端应显示“已观察 9 个自然日，其中 5 天有记录”，不能写成“观察了 5 天”。没有记录的日期不是反例，也不能据此推断某个行为已经停止。

Gate 与幂等必须分开：material_change_watermark 用来决定 run / skip / backlog，包含当前 [D−13, D] 内新增或修改的来源、直接 Context 调整、需执行的 Prompt / Schema / 模型 / 授权配置变更和失败补跑；单纯 target_date 前进、窗口自然淘汰旧日期、候选被 reject / just_once 均不单独触发新调用。source_date<D−13 的新授权或修改只重开对应来源的 historical backlog，不触发最新窗口 API 调用；若它正被 pending / active Context 引用，本地立即把候选标 stale 或把 Context 标 source_stale 并停止进入 Pack，等待历史补 Review。只有 gate=run 后才计算 review_run_key：target_date + 窗口快照 + 来源哈希 + Context revision/hash + 决定反馈 revision + Prompt / Schema / 模型 / 授权配置版本，用于幂等与审计。

历史补 Review 的唯一分窗：超过 14 天仍未 Review、后来新授权，或窗口外文件哈希变化，都会以“文件 + 新哈希”进入 historical backlog。令 start=最早 backlog 来源日期，latest=最新授权来源日期，target_date=min(start+13 天, latest)，模型窗口固定为 [target_date−13, target_date]，但本批只覆盖日期位于 [start, target_date] 的 backlog 来源文件。一次模型调用成功即保存 batch ID、覆盖文件及其哈希并推进这些来源的 reviewed 水位；即使产出待回应候选也表示“已完成 Review”，只是后续分窗暂停到候选处理完。调用失败不推进任何水位；下一批从首个未覆盖来源日期重新计算。每次“继续补 Review”最多一批 / 一次调用。

未回应候选的路由优先级：候选依赖变化先判断证据日期。被改证据仍在当前 [D−13, D] 内，或目标 Context revision/hash、Prompt / Schema、授权范围发生变化时，卡片 stale、按钮立即禁用，并在同一卡位按当前窗口重算；被改证据已经在窗口外时，卡片进入 stale_waiting_backlog，只显示等待历史补 Review，绝不调用不含该证据的最新窗口。新来源、无关 Context 或仅模型版本等不影响当前卡合法性的实质变化则合并进 dirty_watermark，本次 gate=defer、0 次模型调用且不推进成功水位；卡片处理后，在下一次定时或手动 gate 中只按最新窗口运行一次。

source_stale 的恢复条件：active Context 的来源变化后立即停止进入 Pack。自动 evidence_rebased 只允许一种确定性等价情况：整份来源在仅规范化 CRLF/LF 与行尾空白后内容哈希完全相同，全部逐字 quote 仍可定位，statement / scope / category 未变，且 target revision CAS 成功。任何非空文本的新增、删除、改写都必须保持 source_stale，即使旧 quote 仍存在、历史 Review 返回 no_change / reinforce，也不能自动恢复；若语义未变但证据版本变化，reconcile 必须生成一张 update“重新确认依据”候选，用户确认后才创建新 active revision。quote 消失、出现否定或冲突时走 update / conflict；失败或拒绝均不得恢复。

行为与兴趣边界：现有数据基础围绕日级文本中的工作方式、判断特征与变化线索，尚未实现广义兴趣画像或自动习惯采集。当前 profile 中的 continuing 只是内部状态：来自有效 confirmed Context、legacy accurate，或聚合后至少 3 个不同证据日；它仍不等于长期确认，也不应在新前端变成人格标签。广义兴趣、传感器输入和情绪、健康等敏感状态均不在当前范围。

明确的产品决定：处理节奏可以是每日的，打扰节奏必须由“理解是否真的发生变化”决定。如果改成每天都强制用户点一次确认，就会改变当前“不制造 Review 待办、一次只呈现一个局部理解”的产品原则，不属于本 PRD。

Legacy compatibility · Decision semantics

长期洞察只用修改 / 删除；旧五种决定留在兼容区

下方五个按钮只描述旧 Candidate → Confirmed / One-time Pack 链路，不是长期洞察的必经审批，也不出现在正文。它们仅作为任务复用协议收进底部“更新与边界”。

现有数据 reducer：任一合法 reject 都是该 exact unit 的终态删除，后续 edit / scope / accurate / changed 不能复活。最新 edit 与 scope 分维度保留；system_observation / continuing / changing / user_edited 继续作为内部状态，不再作为前台人格标签展示。

前端 P1 反馈合同：一个阅读段落只对应一个 active projected tagId，因此直接复用现有 tag-bound edit / reject。用户编辑仍写原 response hash + insight index 对应的 edit feedback；用户删除先二次确认，reject 写入成功后才从 UI 移除，写入失败则保留 / 恢复原段落并明确报错，成功后当前版本不可撤销。reject 只保证同一 exact semantic key 终态删除；同义改写可能生成新 key 并再次出现，当前没有语义级 suppression 或 restore Schema。

Review 引擎

  • 自动 Context Review 默认关闭，只能由用户明确开启
  • 授权明确覆盖日级原文、相关 Context、最小决定反馈、Provider / 模型与自动运行时机
  • 没有实质变化且无需重试时，08:00 / 21:00 检查均产生 0 次模型调用
  • 21:00 target_date=今天；08:00 target_date=昨天且只补晚间变化、漏跑或失败
  • 窗口严格为 D−13 至 D；历史不足时使用实际授权的 N 个自然日
  • 只有 target_date 前进或窗口自然老化时产生 0 次调用，也不会让待回应卡片 stale
  • 离线超过 14 天时按 start / target_date 唯一算法分窗；成功才推进本批覆盖来源水位，失败不推进
  • 用户每次补历史 Review 最多一个 14 日批次 / 一次调用；产出候选后暂停下一批
  • 窗口外旧文件新增授权或哈希变化只重开 historical backlog，不触发最新窗口 API 调用
  • 候选依赖在当前窗口变化则原位重算；窗口外变化则 stale_waiting_backlog，禁止走最新窗口
  • active Context 来源变化立即 source_stale / 停止入 Pack；仅整源规范化内容等价 + quote 全部可定位时可 CAS evidence_rebased
  • 任一非空文本变化都不得自动恢复；语义未变也须 update 重新确认依据，冲突则经 conflict + 用户确认
  • 保留旧 quote 但新增“以上已作废”等否定语句时必须保持 source_stale，测试不得误恢复
  • 分别计算自然日跨度和有记录天数，缺失日期不作为反例
  • 每轮同时核对相关 active Context，并产出规定的六种结果之一
  • 每个 new / update / conflict 均能回查原始文件、行号和逐字证据
  • review_run_key 包含 target_date、窗口、来源哈希、Context revision/hash、decision feedback 及规则/授权版本
  • 证据或目标 Context 等候选依赖变化才会 stale 并原位重算；模型版本变化本身不失效卡片
  • pending 卡存在时，无关新来源 / Context 或仅模型版本变化记为 defer + dirty，0 调用且不推进水位
  • Prompt / Schema / 授权变化影响候选合同时立即 stale；卡片处理后 dirty 只合并运行一次
